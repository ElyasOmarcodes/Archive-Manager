# د آرشیف چټک مدیر — معماري (Architecture)

## ۱. د بک‌اینډ ژبې انتخاب — Backend language decision

**پریکړه: بشپړ Dart/Flutter — پایتون نه کارول کیږي.**

| معیار | Dart-only | Dart + Python |
|---|---|---|
| د وینډوز خروجي | یو `.exe`، هیڅ اضافي runtime نه | باید CPython (~۴۰MB) + PyInstaller بنډل شي |
| د پروسو تر منځ اړیکه | مستقیم فنکشن کال | IPC/سوکټ — ځنډ او د ناکامۍ نوې نقطه |
| د SQLite سرعت | `dart:ffi` → اصلي C کتابتون | ورته C کتابتون، خو د IPC سرحد سره |
| موازي پروسس | `Isolate` — ریښتینی موازي | `multiprocessing` + serialization |
| ساتنه | یوه ژبه، یو ټیم | دوه سټېکونه |

پایتون هیڅ داسې څه نه ورکوي چې Dart یې ونه‌شي کولی: د لټون درنه برخه په اصل کې د **SQLite** (C کوډ) دننه ترسره کیږي، نه په هوسټ ژبه کې.

## ۲. ولې ۵ ټیرابایټه ډیټا په څو ثانیو کې فلټر کیږي

**بنسټیز اصل: مونږ هیڅکله د لټون پر مهال ډیسک نه سکن کوو.**

د لټون ساحه فایلونه نه دي — **میټاډیټا** ده:

```
۱۰,۰۰۰ پیښې × ~۲KB میټاډیټا = ~۲۰MB
```

دا ۲۰MB په بشپړ ډول د RAM/page-cache دننه ځای نیسي، پداسې حال کې چې اصلي ویډیوګانې ۵TB دي.
نو د لټون وخت د ډرایو له کچې سره **هیڅ اړیکه نه لري** — یوازې د پیښو له شمېر سره.

## ۳. دوه‌پوړیز ذخیره (Two-tier storage)

### پوړ ۱ — حقیقت پر ډیسک: `metadata.json` + `content.json`
هره پیښه خپل دوه فایله لري چې د هغې فولډر دننه پراته دي.
- **د لېږد وړ** — هارډ بل کمپیوټر ته یوسئ، هر څه ورسره دي
- **د انسان لوستلو وړ** — که سافټویر هم ورک شي، ډیټا نه ورکیږي
- **د بیا رغونې منبع** — د ایندکس بیا جوړول تل ممکن دي

#### ولې دوه فایله، نه یو؟

پخوا هر څه په یوه `metadata.json` کې و — بلاکونه، د فایلونو لیست،
درې واړه نېټې. یوه عادي پیښه یې **~۸۰ کرښې / ۲.۵KB** جوړوله. خو د
**فلټر** پر مهال له هغو څخه نیمایي یې هم نه کارول کیږي: سکنر هره
پیښه لولي، JSON یې پارس کوي، بلاکونه او ضمیمې یې په حافظه کې جوړوي —
او بیا یې غورځوي.

نو ډیټا وویشل شوه:

| فایل | څه پکې دي | څوک یې لولي |
|---|---|---|
| `metadata.json` | یوازې د فلټر ډګرونه: سرلیک، کټګورۍ، `jdn`، درجه، رنګ، کیورډونه، شخصیتونه، د فایلونو شمېر/حجم/ډولونه، او د متن څنډل شوې بڼه | **هر سکن** — د هرې پیښې لپاره |
| `content.json` | بلاکونه، د ضمیمو بشپړ لیست، لینکونه | یوازې کله چې کاروونکی پیښه **پرانیزي** |

**پایله (پر ۳,۰۰۰ پیښو کچه شوې):**

| | پخوا | اوس |
|---|---|---|
| د یوې پیښې `metadata.json` | ۲,۵۰۰ B / ~۸۰ کرښې | **۱,۰۳۸ B / ۱ کرښه** |
| د ټول آرشیف د فلټر ډیټا | ۷.۳ MB | **۳.۰ MB** |

#### درې نېټې → یو عدد

پخوا هره پیښه درې واړه تقویمونه پر ډیسک ساتل (`{شمسي:{...},
قمري:{...}, میلادي:{...}}` = ۲۸۷ B). خو دا درې واړه له **یوه**
عدد — د **جولیان ورځې شمېره** (`jdn`) — حسابیږي، او هغه محاسبه
~۲۳µs نیسي. نو اوس یوازې `jdn` ساتل کیږي، او `TriDate` یوازې هغه
وخت جوړیږي چې ریښتیا ورته اړتیا وي (lazy).

#### زړې بڼې ته درناوی

که پخوانی `metadata.json` وموندل شي (`schemaVersion: 1`)، پروګرام
یې **لا هم بشپړ لولي** — هیڅ ډیټا نه ورکیږي. لومړی ځل چې پیښه بیا
ثبت شي، پخپله نوې بڼې ته اوړي.

### پوړ ۲ — مشتق ایندکس: SQLite + FTS5
په `AppData` کې یو `index.db`. کاروونکی یې هیڅکله نه ویني.
- **بیا جوړېدونکی** — که ورک شي، بیا سکن یې جوړوي
- **FTS5 معکوس ایندکس** (inverted index) — د بشپړ متن لټون <۱۰ms
- **د فاسیټ جدولونه** — د Adobe Bridge په څېر ژوندي شمېرې

```
┌─ ډرایو E:\ (۵TB) ─────────────┐      ┌─ AppData ────────────┐
│ 1405/سنبله/13/د کابل تړون/    │      │  index.db            │
│   ├ index.html                │ scan │  ├ events            │
│   ├ metadata.json  ───────────┼─────►│  ├ events_fts (FTS5) │
│   ├ content.json   (پر غوښتنه)│      │  ├ keywords/persons  │
│   └ attachments/*.mp4         │      │  └ facet indexes     │
└───────────────────────────────┘      └──────────────────────┘
         حقیقت                                  چټک لټون
```

## ۴. د Adobe Bridge د فلټر سیستم څېړنه

د Bridge د **Filter Panel** ټول معیارونه چې مونږ یې تطبیقوو:

| د Bridge معیار | زمونږ تطبیق |
|---|---|
| Rating (★ ۰–۵) | `rating INTEGER` + `has_rating` |
| Label / Color | ۸ رنګه ټګ + «بې‌رنګه» |
| Keywords | many-to-many + FTS5 |
| File Type | د ضمیمو له مخې (mp4/jpg/wav/...) |
| Date Created / Modified | د ډیسک تاریخونه |
| **Date (Event)** | زمونږ اضافه: درې‌ګوني تقویمونه |
| Folder / Location | د پیښې فولډر مسیر |
| Orientation / Dimensions | د انځورونو لپاره |
| Persons (Bridge: `Iptc4xmpExt:PersonInImage`) | جلا شخصیت جدول |
| Category | زمونږ اضافه — د پیښې بڼه |

**مهمې ځانګړنې چې د Bridge څخه اخیستل شوې:**
1. **Faceted filtering with live counts** — هر فلټر تر څنګ یې شمېره ښکاري
2. **AND ترکیب د بېلابېلو ډلو ترمنځ، OR د یوې ډلې دننه**
3. **Smart Collections** — ساتل شوی لټون چې پخپله تازه کیږي
4. **Sort** — نوم، تاریخ، درجه، اندازه، ډول

## ۵. د تاریخ ماشین (Tri-calendar)

هر تاریخ په دریو تقویمونو کې ساتل کیږي، **مګر** د پلټنې لپاره یو **Julian Day Number** (integer) هم:

```json
"date": {
  "jd": 2461234,
  "shamsi":  {"y":1405,"m":6, "d":13, "text":"۱۳ سنبله ۱۴۰۵"},
  "qamari":  {"y":1447,"m":3, "d":21, "text":"۲۱ ربیع‌الاول ۱۴۴۷"},
  "miladi":  {"y":2026,"m":9, "d":4,  "text":"۴ سپتمبر ۲۰۲۶"}
}
```

د **`jd`** له امله د هر تقویم د «له… تر…» پلټنه یوازې یو `BETWEEN` دی پر یوه ایندکس شوي عدد باندې — یعنې O(log n).

- **Jalali/شمسي:** `shamsi_date` — د `jalaali-js` الګوریتم، لوړ ازموینه لرونکی
- **Hijri/قمري:** `hijri` — د **ام‌القرا** (Umm al-Qura) جدول
- **ډیفالټ نندارې تقویم:** هجري شمسي (د پښتو میاشتو نومونو سره)

## ۶. د کوډ جوړښت

```
lib/
├ core/       تیم، ژبه، د تاریخ ماشین، ابزارونه
├ data/
│  ├ models/     د ډیټا ماډلونه (Event, EventMetadata, Block…)
│  ├ platform/   د فایل سیسټم لایه (io / web-demo)
│  ├ index/      SQLite FTS5 ایندکس
│  └ repository/ د غوښتنو یوازینۍ دروازه
├ features/   هره پاڼه یو فولډر
└ widgets/    ګډ UI اجزا
```

**د پلیټ‌فارم انتزاع:** `ArchiveBackend` یو انټرفیس دی چې دوه تطبیقونه لري —
`IoBackend` (وینډوز/لینکس: ریښتینی فایل سیسټم + SQLite) او `DemoBackend`
(ویب: د یادښت دننه ډیټا، د نندارې/سکرین‌شاټ لپاره). دا هم د ازموینې اسانتیا ده.
